# 内部机制

README 只讲怎么用。这里讲为什么——阈值怎么算出来的、字段在插件与 DSH 内置压缩之间怎么流动、以及若干限制的成因。

## 阈值是怎么算出来的

### 输入量（不来自配置）

| 符号 | 含义 | 从哪来 |
|---|---|---|
| `contextWindow` | **模型声明的上下文总容量**，输入与输出共用 | 由适配器声明，运行时解析。1M 模型即 1,000,000 |
| `reservedCompletionTokens` | **为本次回复预留的输出 token** | 本次请求信封里的输出上限。声明了 `maxTokens` 的适配器（pi-ai 供应商就是）会填满整段额度，可达窗口的四成——**不可忽略** |

`contextWindow` 是**模型**的属性。换模型，下面所有数都会变。

### 第一步：可用容量

| 符号 | 算式 | 含义 |
|---|---|---|
| `M` | `contextWindow − reservedCompletionTokens` | 真正能放对话内容的量 |
| `B` | `M − 预留` | 允许对话涨到的上限。预留默认 `max(15% × 窗口, 16384)` |

预留用 `reserveTokens` 配置，留空即上式。它只做一件事：让压缩**低于**窗口物理上限，留出余量。

`B` 是**天花板**，不是摆设：对话不可能涨过 `M`，所以任何高于 `B` 的目标都会落到 `B` 上。触发点的高于 `B` 的那部分不存在，提前量最多一个「预留」。

> 只写比例（`thresholdTokens: -1`）时不走锁定，`预留` 取内置压缩自己的 `headroomTokens`（留空 65,536）；显式设置 `reserveTokens` 时两种写法都走同一个值。要两种写法完全一致，就显式设置它。

### 第二步：压缩阈值——两种写法，绝对值优先

| 配置写法 | 压缩阈值 |
|---|---|
| `thresholdTokens: 450000` | `min(450,000, B)`。窗口在运行时折算出比例，换模型也是 450K |
| `thresholdTokens: -1`（默认）+ `thresholdRatio: 0.8` | `floor(min(窗口 × 0.8, B))` → 1M 窗口是 **800,000** |

绝对值还受一道保护：**若它 ≥ `窗口 − 预留`**（永远触发不了），自动退到 `B`。

**两道上限里低的那一道说了算。** 目标高过 `B` 时并不是"算错了"，而是如实退到窗口装得下的最晚一点。

### 第三步：保留量

`keepRecentTokens`，默认 `20000`，绝对值。硬约束：必须 `< 压缩阈值`。

该值只是**预算**，实际保留量只会更大：裁剪以整条消息为单位，切点还需向旧一侧移动以满足 tool-call/tool-result 配对。因此实际保留的是「不超预算的最大整消息后缀」。

> 若显式设了 DSH 内置压缩的 `retainTokens` / `retainRatio`，则它们优先。

### 第四步：提醒位置——推导，不可配

```
lead = min(32000, max(8192, floor(压缩阈值 × 0.125)))
提醒区间 = [压缩阈值 − lead, 压缩阈值)
```

与 omp 一致：`lead` 是算出来的，没有配置项。上限 32000 在压缩阈值 ≥ 256,000 后一直生效，故 1M 窗口下 `lead` 恒为 32,000。

半开区间是刻意的：压缩在 `≥ 压缩阈值` 发生，提醒在 `< 压缩阈值` 生效，**同一步里不可能既提醒又压缩**。

### 实例：`thresholdTokens: 450000`（1M 窗口）

| 量 | 算式 | 值 |
|---|---|---|
| 预留 | max(1,000,000 × 15%, 16384) | 150,000 |
| `M` | 1,000,000 − 393,216 | 606,784 |
| `B` | 606,784 − 150,000 | 456,784 |
| 压缩阈值 | `min(450,000, B)` | **450,000** |
| 保留量 | 默认 | **20,000** |
| `lead` | min(32000, floor(450,000 × 0.125)) | 32,000 |
| 提醒区间 | [450,000 − 32,000, 450,000) | **[418,000, 450,000)** |
| 单次压缩量 | 450,000 − 20,000 | 430,000 |

这里的输出预留取 393,216（pi-ai 供应商声明 `maxTokens` 后的量级）。若目标设为 500,000，`B` 只剩 456,784，实际会落在 **456,784** 上——早 43,216，恰好在预留之内。把 `reserveTokens: 32000` 显式设小，`B` 抬到 574,784，500,000 就能精确命中。

全默认（`thresholdTokens: -1`）时压缩阈值回落到 `min(窗口 × 0.8, B)`，1M 窗口即 800,000，提醒区间 [768,000, 800,000)。

### 三个易错点

1. **提醒位置不可单独调整。** 它只随压缩阈值变化。
2. **压缩阈值的绝对值不受模型影响。** 窗口在运行时解析后折算，故 200K 与 1M 模型都落在配置值上；仅当该值 ≥ 窗口时退让。
3. **`reserveTokens` 是压缩阈值下方的余量，和输出预留各自独立。** 两者都从同一个窗口里扣，但含义不同：输出预留是给本次回复的额度，余量是给"判定之后到下一条请求之间"的增长留的空。**余量绝不能从目标反推**——写成 `窗口 − 目标` 就等于把输出预留又扣了一遍，450,000 会掉到 `450,000 − 输出预留`。

## 字段怎么流到 DSH 内置压缩

DSH 内置压缩严格校验配置：不认识的键直接拒绝。所以本插件自己的三个字段不能原样传下去，必须翻译：

| 插件字段 | → 内置字段 | 说明 |
|---|---|---|
| `keepRecentTokens` | `retainTokens` | 同为绝对值、同样的 `< 压缩阈值` 约束；保留逻辑仍由内置实现执行 |
| `reserveTokens` | `headroomTokens` | 同一个"从压缩阈值往下留多少"的量 |
| `thresholdTokens` | （不翻译） | 绝对值需要模型窗口，而构造时窗口未知；改为在每轮开始时锁定 |

**显式设置的内置字段优先**：这些插件字段带默认值，若不加此规则，从未设置过 `retainTokens` 的配置会被默认值覆盖。

### 绝对值的压缩阈值是怎么锁定的

窗口由适配器声明、运行时才解析，而内置压缩的策略在构造时就冻结了。所以：

1. 插件自己的 `agent/pre-step` 监听器**排在**内置压缩之前执行（`{ prepend: true }`）；
2. 它在此已 `await` 到窗口（提醒逻辑本来就要用）；
3. 拿到窗口后换掉内置压缩的配置对象——比例设为 `压缩阈值 / 窗口`，`headroomTokens` 设为**那个固定的预留**（`reserveTokens`，留空即 `max(15% × 窗口, 16384)`）。

**为什么不是 `窗口 − 压缩阈值`。** 内置压缩的阈值是两道上限取小：`min(窗口 × 比例, M − headroomTokens)`。把 `headroomTokens` 写成 `窗口 − 目标`，第二道就变成 `目标 − reservedCompletionTokens`——输出预留被扣了两次。1M 窗口、输出预留 393,216、目标 450,000 时，实际触发点是 **56,784**（窗口的 5.7%），而不是 450,000。写固定的预留，阈值就是 `min(目标, M − 预留)`：要么精确命中目标，要么如实退到窗口装得下的最晚一点，提前量不超过一个预留。

内置压缩的三条路径（自动压力、手动 `/compact`、溢出恢复）都读这个对象，所以三条都生效。

## 为什么有些配置改不动

> **DSH 自身的压缩配置只能改配置文件（profile 的 YAML），dsh 启动时读一次，改完必须重启 dsh。**

这些字段不出现在设置页：

`auto` / `thresholdRatio` / `headroomTokens` / `retainRatio` / `retainTokens` / `maxTokens` / `summarizationProvider` / `summarizationModel` / `compactionRetries` / `maxOverflowRetries` / `modelPolicies`

两个原因，都是刻意的：

1. **它们不出现在表单里。** 设置服务只渲染有 volatile 祖先的字段，普通字段被当作「普通配置」排除。我们在 `schema.ts` 里把内置压缩的 schema 原样铺开、**没有**标 volatile。
2. **即使改了也不会立刻生效。** 内置压缩在构造时就把这些配置解析进自己的 `this.config`，之后不再重读；而 volatile 提交不会重新构造实例。

把它们标成 volatile 会更糟：内置压缩按**值**读这些字段（`config.headroomTokens ?? 65536`），拿到句柄会让它的算术出错、并在挂载时被 `validateKeys` 拒绝。

## 其它实现细节

- **笔记本的投递顺序。** 修订版本作为**延迟上下文**随工具结果一起送达，因此在工具结果**之后**进入上下文，不会打断 provider 要求的 `assistant(tool-call) → tool(result)` 相邻关系。
- **笔记本落在 `user/message` 上。** DSH 0.2.0-rc.2 要求未知事件类型携带 `ignorable` 标记才能被重新加载，而 SDK 没有写入该标记的接口，所以无法声明自有事件类型。详见 `src/notebook.ts` 顶部论证。
- **摘要外面还有一层壳。** 内置压缩把每段静态摘要包进 `CHECKPOINT_PREAMBLE` + `<compacted-summary>`；除非重写整个事务，否则这层去不掉。内层的 `<context-window-rollover>` 块逐字保留。
- **`enabled: false` 不是卸载。** 工具在挂载时注册，volatile 提交不会重新挂载，所以关掉后工具仍在模型的目录里，只是每次调用被拒（下一次调用起）。要从目录里消失得重启 app。
